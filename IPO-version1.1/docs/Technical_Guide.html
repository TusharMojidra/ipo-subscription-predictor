🎯 High-Level Overview

What does this project do?

We built a machine learning system that predicts two things about upcoming Indian IPOs:

PredictionWhat it answersHow
Subscription Tier "Will this IPO be oversubscribed (hot) or undersubscribed (cold)?" Classification — Low / Medium / High
Listing Gain "How much will the stock price rise (or fall) on listing day?" Regression — predicts a percentage
In 2 sentences: Our system learns from 648 historical IPOs (2010–2026) how issue size, offer price, and subscription data relate to listing performance. It then uses that pattern to predict the outcome for a brand-new IPO.

Why is this useful?

When a new IPO launches, investors want to know: "Should I apply for this?" Our tool gives them a data-driven estimate before the stock lists, based on patterns from hundreds of past IPOs.

📥 The IPO (Input → Process → Output) Model

📥 Input — What data enters the system?

We start with a CSV file containing 648 IPO records scraped from the Indian primary market. Each row represents one IPO and has these columns:

ColumnExampleWhat it means
IPO_NameNMDC LimitedCompany name
Date2023-11-28Listing date
Issue_Size(crores)4500Total ₹ being raised
Offer_Price₹183Price per share in the IPO
QIB32.5×Institutional investor oversubscription
HNI18.7×High-net-worth individual oversubscription
RII8.2×Regular retail investor oversubscription
Total21.4×Total oversubscription (times)
List Price₹206Price on the first trading day
Listing Gain+12.6%This is our target — what we predict

⚙️ Process — What happens to the data?

1
Clean the data

Remove duplicates, fix bad dates, fill missing values with medians, cap extreme outliers.

2
Engineer features

Create log-transformed columns (because subscription data is heavily skewed) and demand-ratio features (QIB share, HNI-to-QIB ratio, etc.).

3
Split data (out-of-time)

Train on IPOs from 2010–2023, test on 2024–2026. This simulates real prediction: we never peek at the future.

4
Train models

Classification (Random Forest, Logistic Regression, SVM) + Regression (Huber, Gradient Boosting, Random Forest). GridSearchCV finds the best parameters.

📤 Output — What do we deliver?

  • Interactive web dashboard (Streamlit) where users enter IPO details and get instant predictions
  • Subscription tier — Low / Medium / High with confidence percentages
  • Listing gain estimate — e.g., "+12.6% (typical error ±18 points)"
  • SHAP explainability — shows which feature pushed the prediction up or down
  • 3D visualizations — interactive scatter plots of the IPO dataset

📂 File-by-File Breakdown

🐍
main.py
root/

Purpose: The master orchestrator. Runs the entire offline pipeline from one command: python main.py

What it does (step by step):

  1. Calls load_data() from data_loader.py to read the raw CSV
  2. Calls clean_data() → drop_unusable_rows() → fill_missing_values() → winsorize_outliers() from preprocessing.py
  3. Calls add_subscription_class() from feature_engineering.py to create the Low/Medium/High target
  4. Saves cleaned data to data/processed/cleaned_ipo_data.csv
  5. Calls run_eda() to generate charts
  6. Calls run_classification() and run_regression() to train models

Imports: Everything from src/ — data_loader, preprocessing, feature_engineering, eda, models_classification, models_regression

🐍
src/data_loader.py
src/

Purpose: One-liner — reads the raw CSV into a pandas DataFrame.

import pandas as pd

def load_data(path):
    return pd.read_csv(path)

Why a separate file? Keeps the I/O separate from logic. If we later switch to a database or API, we only change this one function.

Passes data to: main.py → then to preprocessing.py

🐍
src/preprocessing.py
src/

Purpose: Clean the raw data. This is where we turn messy, real-world data into something models can learn from.

4 functions, each doing one job:

FunctionWhat it does (in plain English)
clean_data(df) Strips whitespace from column names, converts Date to datetime format, converts numeric columns from text to numbers, drops rows with unparseable dates. Also extracts Year from the date.
drop_unusable_rows(df) Removes rows that are missing the target (Listing Gain) or missing ALL subscription data. Also fixes a data error where List Price == 0 (treats it as missing).
fill_missing_values(df) Fills any remaining NaN values with the column median. We use median instead of 0 because zero would corrupt price columns.
winsorize_outliers(df) Caps extreme values at the 1st and 99th percentile. This prevents one mega-IPO from dominating the model's learning.

Imports: pandas, numpy

Passes data to: Back to main.py → then to feature_engineering.py

🐍
src/feature_engineering.py
src/

Purpose: Create new, more useful columns from the existing data. This is often the most important step — better features = better predictions.

Key functions:

FunctionWhat it does
add_log_features(df) Applies log1p transformation to subscription columns (QIB, HNI, RII, Total) and price columns. Why? Because subscription data is heavily right-skewed — a few IPOs have 100× oversubscription while most have 5×. Log compresses this so the model treats all IPOs fairly.
add_demand_ratios(df) Creates share-of-demand features: QIB_share (what % of demand is institutional), RII_share (retail %), HNI_to_QIB ratio. These are the top predictors in similar published projects.
add_subscription_class(df) Categorizes Total subscription into 3 tiers: Low (<2×), Medium (2×–10×), High (≥10×). This creates the classification target variable.

Imports: numpy, pandas

Passes data to: Saved to data/processed/cleaned_ipo_data.csv

src/models_regression.py
src/

Purpose: Predicts the listing gain percentage using 6 log-transformed features: log_QIB, log_HNI, log_RII, log_Total, log_Issue_Size, log_Offer_Price.

Why log-transformed? Raw subscription data ranges from 0.5× to 200×. Log1p compresses this to a range the model can handle linearly.

Models tested:

ModelBest R²Notes
Huber Regression~0.30Winner — robust to outliers in the target
Linear Regression~0.25Baseline — assumes linear relationship
Gradient Boosting~0.22Tends to overfit on small data
Random Forest~0.18Overfits — not enough training data

Why Huber wins: Listing gains have extreme outliers (some IPOs gain +300%, others lose -40%). Huber regression ignores these extremes during training, while other models chase them.

predict_ipo.py
root/

Purpose: The prediction engine. Used by both the Streamlit dashboard (app.py) and the CLI demo. Trains models on the full dataset and caches them to disk.

Key functions:

FunctionWhat it does
load_training_data() Loads cleaned_ipo_data.csv. If missing, rebuilds it from raw data (safety net).
train_models(df) Trains the Random Forest classifier + Huber regressor. Caches to models/ipo_models.joblib so the next start is instant. Only retrains when the data changes (uses a file hash).

🎙️ Anticipated Coordinator Questions

Here are 6 tough questions your coordinator might ask, with simple confident answers:

❓ Q1: "Why is the classification accuracy only 62%? That seems low."
A: It's important to clarify that 62% is the out-of-time accuracy — we test on IPOs from 2024–2026 that the model has never seen. Random guessing on 3 classes would give 33%, so 62% is nearly double that. The task is inherently hard because IPO demand depends on market sentiment, which changes over time. Comparable published projects report 60–69% on similar tasks. Also, balanced accuracy is low because the classes are imbalanced — Medium is the majority class. We use class_weight='balanced' to mitigate this.
❓ Q2: "Why did you choose an out-of-time split instead of random train-test split?"
A: A random split would let the model "peek into the future" — it might train on a 2025 IPO and test on a 2024 IPO, which inflates accuracy. In the real world, we're predicting future IPOs we haven't seen yet. The out-of-time split (train on 2010–2023, test on 2024–2026) simulates this reality and gives us a more honest estimate of real-world performance.
❓ Q3: "Why use log transforms? What happens if you don't?"
A: Subscription data is heavily right-skewed. Most IPOs get 5–20× oversubscription, but a few get 100–200×. Without log transforms, the model would treat the 200× IPO as an extreme outlier and distort its learning. log1p compresses the range: log(5) ≈ 1.6, log(200) ≈ 5.3. This makes the distribution more normal and helps linear models converge. In our experiments, log features improved R² by ~0.3 points compared to raw features.
❓ Q4: "Why Huber regression over Random Forest for listing gain?"
A: Listing gains have extreme outliers — some IPOs gain +300%, others lose -40%. Random Forest tends to overfit to these extremes on a small dataset (648 rows). Huber regression uses a loss function that's quadratic for small errors but linear for large errors, meaning it essentially ignores the extreme outliers during training. This makes it more robust. Our R² improved from 0.18 (RF) to 0.30 (Huber) with the same features.
❓ Q5: "How does the model caching work? Won't it serve stale predictions?"
A: We use joblib.dump() to save trained models to disk. On the next app start, we compute an MD5 hash of the cleaned CSV. If the hash matches the cached one, we load from disk (instant). If the data changes (new IPOs added), the hash won't match and the models retrain automatically. In the Streamlit app, we also use @st.cache_resource which keeps models in memory across reruns. So no — stale predictions are impossible as long as the data file is updated.
❓ Q6: "What would you improve if you had more time?"
A: Three things: (1) More features — sector/industry encoding, grey market premium (GMP), company fundamentals (revenue, profit). These are available from IPO review sites. (2) Larger dataset — 648 IPOs is small for ML. We could augment with NSE/BSE historical data going back to 2000. (3) Time-series modeling — market sentiment shifts over time. An LSTM or transformer model could capture temporal patterns that a static model misses.
